# ADR-0513: Package recorded taskspace memory replay

## Context

The accepted220-row candidate repaired known-TRAIN Pick19 and retained three
earlier endpoints. Its research case depended on ignored artifact history and
one producer environment, which prevented ordinary local reproduction.

## Decision

Distribute the generated numeric TRAIN episodes and four complete recorded
trajectories as a small JSON example. A thin adapter validates roles, identities,
causal replay history and recorded sparse outcomes, then composes the existing
six-release stream and nearest predictor. A separate CLI owns file access and
exclusive output. No learning objective or runtime framework changes.

Keep recorded outcomes separate from offline command matches. Never append replay
records to training or treat CPU reconstruction as a fresh simulator episode.
Use the repository's existing canonical context helper, including Pick17's
`pick-cube` name. Minimal CPU requirements use the existing NumPy dependency.

## Alternatives

Requiring archived source loaders would retain the demonstrated portability
dependency. Copying a trained model would hide reconstruction costs. Rerunning
native scenes solely to reproduce stored commands would add unnecessary physics.

## Consequences

All220training rows and70commands remain inspectable. Windows/Linux and an
isolated source/data copy reproduce them without SDK imports. Actual qualification
includes an initial context refusal and recorder collision; successful reports
were recovered byte-for-byte from stdout, without rerunning models.

Fresh installation, a portable optional native path, upstream asset/setup terms,
comparative scientific benefit and release readiness retain separate gates.
