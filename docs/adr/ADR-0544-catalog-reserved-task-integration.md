# ADR-0544: Catalog-objective reserved-task integration

## Context

The catalog learner and isolated catalog probe are accepted software. A fixed
catalog main-stream case remains mixed, including invoice failure. Existing paired
probes show only partial task learning. The new objective needs an isolated
fresh-task observation with unchanged markers, dose and metrics.

## Decision

Extend the existing reserved-task app and temporal CLI with explicit catalog mode.
Each phase binds two probe queries to all three current candidates and canonical
target indices. Keep probe_train features distinct from benchmark TRAIN. Reuse
inbox, clocks, separate consent/budgets, native ownership and prior paid-prefix
guards. Record objective/IDs/indices and exact candidate/logit exposures, then
admit the complete main/child evidence before cached scoring.

## Alternatives

A new runner would duplicate causal and ownership rules. Reusing paired positive
action records would lose full-catalog supervision. Broadening TRAIN admission or
silently changing the default objective would blur isolation and invalidate prior
evidence. Additional checkpoint/provenance infrastructure is not needed.

## Consequences

Paired defaults and support restrictions remain; the implemented catalog/reserved
CLI combination replaces its old refusal expectation with positive and misbinding
checks. Software acceptance and the single native observation have separate gates.
Both main and probe objectives change relative to historical paired results, so
no isolated causal or matched-total-compute conclusion follows. The16-template
feature union binds its own token/control/baseline state before any update; the
accepted12-template catalog result is not assumed numerically identical. All
negative outcomes and unfinished wider requirements are preserved.
