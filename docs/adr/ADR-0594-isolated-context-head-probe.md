# ADR-0594: further learning on isolated contextual heads

## Context

77solves/retains four known tasks across public contexts, but separation protects
the other head, not earlier skills within one head. Existing generic probe/return
already accepts D9and complete opaque state; native ticket recipe was BP/D7-only.

## Decision

Add explicit separate-head mode to that recipe, share run_arm/endpoints/validation,
and isolate source/data/guard preparation in a small helper. Preserve native mode.
Use unused known TRAINlegacy templates, homogeneous percontext; warm/fresh96coef
controls, original16probe/16return/checkpoints, oldfourtaskTRAINmonitors andsix
endpoint workflows. Both phase budgets are born once at arm start, not renewed.
Source77history stays charged; data/owners/RNG/prior paid row containers/values
are protected before more work. Probe weights never become deployment weights.

## Alternatives and consequences

A new probe runner duplicates accepted isolation/return code. Repeating77training
or accessing final examples is unnecessary. More replay sweeps do not answer
within-head learnability. Source and fresh histories differ; no equal-all-in cost
or general/CPC claim follows. Warm learns v1legacy, temporarily loses password,
then returns to six successful workflows. v2legacy was inherited. Fresh learns
legacy, then loses v1legacy while learning old tasks. Preserve all outcomes/costs.

Original protocol named margins that generic reports do not capture. Raw results
are immutable; a prospectively bounded reference supplement computes them from
saved observed weights, using zero-mistake-suffix coefficient equality at4/8 and
verifying all recorded scores/decisions. This is explicitly inferred data and a
protocol deviation with extra288reference rows, not reused original forwards,
invented intermediate counter snapshots or another training run.

Next move qualified source77through existing serving/guard ports, never private
probe weights. Mixed-context read-only prediction and non-Torch byte/typed-serving
adapters are concrete prerequisites, not grounds for a new orchestration layer.
