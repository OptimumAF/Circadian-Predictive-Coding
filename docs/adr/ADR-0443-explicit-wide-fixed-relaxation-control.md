# ADR-0443 — Compose the existing fixed64 control with explicit H32

## Context

Original H32 S2 PC proposals descend locally on fixed TRAIN snapshots, yet latent
gradients remain nonzero and source128 fits stay5/9 percue. H8 fixed64 PC/neutral
controls already exist and remain negative35/54TRAIN,0/6exact. Neither observation
establishes plateau cause, convergence or benefit. Width/horizon recipes require
complete native policy checks; outer fixed64 names differ from native base names.

## Decision

Compose existing pc_relax64/neutral_cpc_relax64 with explicit wide_neural=True on
the original joint128/source0+128/F16/old-A/A16 route. Reuse existing native
learner/stream/probe/return ports. Extend the existing policy helper with exactbool
width selection, preserve H8/False and all original S2 recipe names. Shared
snapshot/training and facade/CLI gates admit only exact registered fullpolicies
and original54*point benchmark clocks. Refuse replay/F48/games/diagnostics here.

Declare actual H32 native policy/neutral config and9735parameters/38940arrayB.
Use64*returned rows for nominal latent costs, retain unobserved work asunknown.
Keep final/probe data out of training beyond original separately reserved F
probe_training; benchmark/deployed learner unchanged by probes. Freeze and review
small native protocols after correctness gates; preserve all outcomes and doses.

Why this: answer one predeclared finite-relaxation sensitivity question with
existing modules.64 is the existing maximum endpoint, not a selected winning
hyperparameter. No new objective, orchestration, capture or baseline retuning.

## Alternatives

Inferring width/horizon from snapshots admits unregistered recipes and hides
costs. Relabeling S64 as original PC changes a frozen baseline. Rebuilding a
learner or runner duplicates existing behavior. Further rate/seed sweeps lack
justification before this sensitivity observation and matched neutral control.

and one PC observation do not imply release readiness or useful acquired recovery.
