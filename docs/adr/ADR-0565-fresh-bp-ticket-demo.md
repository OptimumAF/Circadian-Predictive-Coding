# ADR-0565 — Explicit fresh BP ownership in the existing live recipe

## Context

Portable saved examples work. Fresh BP adaptation still depends on a historical
qualified JSON hash; the live peer recipe deliberately excludes BP. A fresh user
cannot run the successful candidate sequence without developer artifacts.

## Decision

Add an explicit strict fresh-BP opt-in to the existing one-stream recipe. Preserve
peer invocation/report/admission and the old fixed-source route. Start a new BP
candidate/actor/seed and one complete112update budget; keep native algorithms,
data, phases, endpoints, roles and guards unchanged. Distinct report family/role
and inspector note identify fresh charges without prior authority. No state
reader, framework, comparison or parameter tuning. Tiny tests precede one fixed
installed validation with old payload/teacher/task equality checked after work.

Why this: reusing working orchestration solves the actual fresh-user dependency
and charges its full training, without another checkpoint/loader increment.

## Alternatives

- Relax the historical input hash: changes evidence admission unnecessarily.
- General state-loading framework: unrelated to training a fresh owned candidate.
- Admit BP silently in peer mode: changes that protocol's semantics and budgets.
- Repeat the comparative cohort: adds work without verifying the new opt-in path.

## Consequences

The installed path works under an existing optional CPU Torch profile. Stable
serving is still initial/unchanged; task decisions use frozen candidate copies.
Learned serving/promotion is a separate next integration through existing runtime
ports. One fixed engineering run is not independent replication, broad learning,
recovery from forgetting, safety, CPC benefit or whole release readiness.
