# ADR-0329: Probe owned key/door checkpoints through the existing runner

## Context

The accepted recurrent behavior-cloning case has no successful live episodes.
The categorical complete-episode probe now supports the actual K5 learner, but
old saved benchmark JSON contains parameters rather than a restorable optimizer
and gradient checkpoint. A failed tiny exposure does not establish inability to
fit a reserved fresh task.

## Decision

Add one explicit CLI scenario to the existing key/door recipe. Its observer
passes complete owned native states at fixed wake points 0 and 8 into the existing
disposable probe app. A small adapter helper retains planned slots, full curves,
separate original probe budgets, binding/state checks and partial failures.
Reserve E probe roles at collection; keep original benchmark data, updates,
replay authority and final scoring separate. Freeze one tiny local protocol,
including all probe computation and memory exclusions, before native execution.
Retain all endpoint signs; no metric, seed, rate or budget tuning after outcomes.

## Alternatives

Parameter-only reconstruction would lose optimizer/gradient provenance. A new
stream runner would duplicate accepted scheduling and isolation. Additional
training of the final-scored benchmark would mix diagnosis and tuning. Repeating
accepted BP/PC baseline experiments would not answer the in-process question.

## Consequences

The existing recurrent prefix is executed once to supply live opaque checkpoints;
its entire benchmark trajectory must match the accepted case despite probes.
Four disposable cohorts add 64 native updates/512 rows and 32 classification
calls/256 rows. Deterministic E test traces share the training trace domain, so
fit changes establish neither generalization nor navigation skill. Original
routes and all prior failures remain preserved. Full recurrent RL/R4.2 and
repository release claims require separate substantive evidence.
