# ADR-0592: contextual queue replay through existing rehearsal

## Context

75's fresh contextual stream learns both task sets, loses old invoice duringB
and recovers it on return while losing new invoice.74joint fit demonstrates the
same fixed tasks are jointly learnable. Existing rehearsal accepts one complete
episode per wake; contextual wakes contain two tickets and six rows.

## Decision

Compile each existing packet as an explicit ordered two-ticket queue. Validate
each real sandbox commit, then advance to the next ticket. Preserve terminal-only-
at-end episode invariant, authentic inputs/labels, original twelve wake updates,
label clocks and permissions. Parameterize existing trajectory compiler/helper/
receipt checker forD9/sixsteps, retaining D7defaults and complete owned data.
Use existing recent and coverage replay, same two-slot array caps/every2wake/
six-rowevent allowance. Freeze study before execution; no new runner/core codec.

## Alternatives

Joining two terminal individual episodes would violate the codec. Splitting wakes
changes receipt chronology and budget counts. Broadening core multi-episode APIs
is unnecessary for this fixed ordered queue. Increasing doses or adding CPC would
not isolate the present retention/acquisition tradeoff.

## Consequences

Both sole cases complete. Recent repeats no-replay outcomes; coverage preserves
old invoice at B readout while new invoice fails. Final success remains3/4.
Replay adds50%optimization/exposure and storage; coverage has explicit TRAIN-context
metadata. No efficiency, CPC or general scientific advantage follows. All negative
results and costs remain. Next test a conventional public-context separate-head
control with explicit increased capacity, rather than another replay dose sweep.
See docs/context-queue-rehearsal.md and issue76 for limits/evidence/next action.
