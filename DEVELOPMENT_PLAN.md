## Purpose and review boundary

Continue the existing project rather than rebuilding it. Turn its wake/sleep, chemical-gating, replay, and structural-plasticity mechanisms into a well-specified, reproducible research system. Determine where circadian predictive coding actually helps, what causes any benefit, and what accuracy, forgetting, compute, and memory tradeoffs it introduces.

This plan is based on a static review of repository documentation, the NumPy predictive-coding and circadian implementations, the Torch head implementation, benchmark orchestration, continual-shift profiles, CI configuration, and selected tests. No local test suite or training run was completed during preparation: fetching a local clone was blocked by network name resolution. Findings below distinguish observed code behavior from questions requiring tests. Re-audit the current checkout before implementation; the repository may have changed since the inspected commit.

The project is an algorithmic learning research project. “Circadian” describes its wake/sleep-inspired control scheme; it is not evidence of a biological circadian oscillator or a clinical circadian-prediction model. The current “reward” mechanism is supervised batch-difficulty scaling, not an environmental reinforcement-learning reward.

## 3. Research objective and scope

The first defensible milestone is a reproducible answer to:

> Under controlled representations, data access, capacity, memory, and compute budgets, when do chemical gating, sleep consolidation, and structural adaptation improve retention or adaptation relative to ordinary predictive coding and backpropagation?

Predefine four primary hypotheses:

**H1 — Plasticity control.** Chemical gating can improve retention/adaptation tradeoffs compared with otherwise identical ordinary predictive coding.

**H2 — Structural adaptation.** Split/prune decisions can improve the accuracy–capacity or accuracy–compute tradeoff beyond fixed-width and simple scheduled-growth controls.

**H3 — Consolidation.** Replay and homeostasis contribute independently of extra data exposure and training updates. Compare against replay-equipped PC and backprop, not only no-replay baselines.

**H4 — Scheduling.** Adaptive sleep decisions offer a better tradeoff than periodic sleep under a declared sleep/compute budget.

Success does not require winning every benchmark. A useful outcome is a stable implementation and a clear account of where each hypothesis is supported, contradicted, or unresolved.

Near-term scope: correctness, matched benchmarks, transactional sleep, bounded replay, reliable experiment artifacts, controlled continual-learning studies, and measured performance improvements. Defer direct ResNet convolutional rewiring, large generative replay systems, distributed training, and broad architecture searches until smaller experiments justify them.

## 8. Phase 4 — Improve replay and control policies through isolated experiments

**Dependencies:** P2 and P3.  
**Goal:** Make mechanisms useful and interpretable without expanding the hyperparameter surface blindly.

- [ ] **P4.1 — Audit replay retention.** Trace what existing batch snapshots store, how many distinct examples persist after a distribution shift, how priorities age, and whether old-task content survives. Do not assume a buffer measured in batches has a fixed example or byte budget.
- [ ] **P4.2 — Introduce explicit replay budgets.** Bound retained examples and bytes; log duplicate IDs and distinct example exposure. Compare recent FIFO and reservoir retention first. Add class/task balancing only with a declared label/task-information policy and matched controls.
- [ ] **P4.3 — Control replay side effects.** Decide whether replay advances wake chemistry, neuron age, cooldowns, reward baselines, and sleep scheduling. Separate clocks and flags accordingly. Replay must not recursively refill itself or consume validation/test examples.

## 10. Phase 6 — Run controlled ablations and broaden continual-learning evidence

**Dependencies:** P1–P5.  
**Goal:** Answer the hypotheses with measured uncertainty, not a single best run.

### 10.1 Stage experiments by cost

- [ ] **P6.1 — Smoke suite.** Use tiny deterministic synthetic fixtures to test every enabled branch and all artifact outputs. Include deliberately forced sleep events and a stationary control. Smoke results establish functionality only.
- [ ] **P6.2 — Reproduce corrected toy profiles.** Run the existing baseline, strength-case, and hardest-case scenarios under the new protocol. Preserve their original tuning history. Report changes caused by corrected mathematics/protocol separately from new policy improvements.
- [ ] **P6.3 — Run a staged mechanism matrix.** Begin with a few development seeds and a small number of factors. Establish a fixed budget before expanding. Reserve independent confirmation seeds/configurations and final test sets before selecting winners.
- [ ] **P6.4 — Extend the stream protocol.** Add A→B→A recurrence and longer A→B→C sequences, stationary noise, abrupt/gradual drift, and low-data adaptation. Log phase/task information available to each method; future task boundaries must not be an undeclared advantage.
- [ ] **P6.5 — Add a modest real-data continual task.** After multiclass/data-contract readiness, select a small split or transformed-image benchmark. State whether the task is domain-incremental, task-incremental, or class-incremental; use the correct output/head and task-ID assumptions.
- [ ] **P6.6 — Run frozen-feature vision comparisons.** Start with a small controlled dataset/subset and shared representation. Expand to CIFAR-100 only after smoke, matched-head, and protocol checks pass. Keep end-to-end backprop separate.
- [ ] **P6.7 — Confirm promising or informative results.** For inexpensive experiments, plan roughly ten independent confirmation seeds when feasible; use pilot variability to justify final sample size. Smaller GPU studies must be labeled exploratory when uncertainty remains large. Do not stop a seed sweep when rankings become favorable.

### 10.2 Minimum comparison matrix

| Variant | What it isolates |
|---|---|
| Matched backprop head | Learning-rule reference with the same representation and head shape. |
| Ordinary PC | Circadian control reference under the specified PC formulation. |
| PC + chemical gating only | Plasticity gating without sleep or extra replay work. |
| PC + replay, no structural changes | Consolidation without growth/pruning. |
| PC + periodic structure, no replay | Structural control under a simple schedule. |
| PC + homeostasis/reset, fixed width | Nonstructural sleep effects. |
| Full circadian | Combined mechanism under recorded costs. |
| Full circadian minus one component | Contribution of replay, gating, structure, scheduling, or difficulty modulation. |
| Backprop + matched replay | Whether memory access explains retention improvements. |
| Wider fixed PC/backprop | Whether more capacity alone explains the result. |
| Scheduled/random growth control | Whether usage-aware selection beats simpler capacity allocation. |

A fixed-width model chosen after observing the circadian model's final width is a retrospective capacity/oracle reference. Label it accordingly; do not present it as a fair online deployment policy or as equal total training compute. Include planned-width references as well.

### 10.3 Metrics and statistical analysis

- [ ] **P6.8 — Predeclare primary metrics.** Use final average task accuracy and forgetting/retention for continual learning, with adaptation speed or accuracy-over-stream as secondary outcomes. Retain the existing balanced score as a secondary diagnostic rather than the sole ranking criterion.
- [ ] **P6.9 — Record the accuracy matrix.** Let `A[t,j]` be held-out accuracy on task `j` after stage `t`. Compute retention and forgetting from explicit stored values; handle undefined denominators and negative/positive transfer transparently. Evaluate final tests without feeding results back into model selection.
- [ ] **P6.10 — Measure resource costs.** Report wall time, wake updates, latent iterations, replay exposure, sleep/guard overhead, peak memory, replay bytes, initial/final/peak parameters, and parameter history. Show accuracy/forgetting against compute and memory instead of a single composite winner.
- [ ] **P6.11 — Use seed-level paired analysis.** Report individual seeds, mean, dispersion, confidence intervals, and paired differences on shared data/split seeds. Treat runs/seeds—not individual minibatches—as the replication unit. Predeclare primary contrasts and avoid selective multiple-comparison reporting.
- [ ] **P6.12 — Publish failures and null findings in the report.** Preserve divergence, timeouts, rejected sleeps, and regressions. Explain whether a hypothesis is supported, rejected, or unresolved within the measured setting. Distinguish tuning results from independent confirmation.

**Exit gate:** Each primary hypothesis has a reproducible result or a clearly documented remaining uncertainty. No ranking depends on test-informed tuning, unmatched replay privileges, undisclosed capacity growth, or cherry-picked seeds.

Default compute policy: start on CPU with tiny models; detect actual GPU and memory instead of assuming hardware; progress to small GPU runs; estimate sweep cost; enforce budgets; preserve failures; and reserve long confirmation runs for explicit documented candidates. Proposed future config/runner interfaces are not executable commands until implemented and documented.

### Definition of done for an individual coding task

The intended behavior is implemented, relevant tests are added, required checks pass without hiding relevant skips, documentation/configuration is updated, and the evidence log points to exact commands and outputs. An unavailable GPU benchmark remains unverified rather than being inferred from a CPU test.

### Definition of done for an individual experiment

The preregistered local protocol and budgets were followed, all intended seeds and failures are accounted for, raw outputs and metadata are saved, analysis is reproducible, and the hypothesis decision is written. The result may be positive, negative, or inconclusive.
